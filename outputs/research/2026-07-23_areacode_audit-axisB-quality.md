# 행정구역코드 변환 도구 — 디자인 감사 (축B: 완성도)

- **검수일**: 2026-07-23
- **검수 축**: 완성도 (Production Quality) — 절대적 품질 기준 적용
- **검수 대상**: `index.html`, `css/style.css`, 실제 화면 스크린샷 4장(변경 이력 / 시도코드 조회 / 지역코드 변환 / 법정동 검색)
- **매체**: 반응형 웹(데스크톱 1440 우선 + 640 이하 모바일), 바닐라 HTML/CSS/JS, GitHub Pages 정적 배포
- **전제**: 개선 브리프·비즈니스 목표는 전달받지 않음. 오직 결과물과 매체 정보만으로 판단. (목표 적합성은 본 감사의 범위 밖)

## 1. 총평

완성도 관점에서 이 결과물은 **평균 이상의 성숙한 정적 도구**다. 특히 디자인 토큰 체계(색 스케일·radius·shadow·transition을 CSS 변수로 일원화, `style.css:15–59`)와 "바뀐 자릿수만 앰버로 짚어주는" 전용 시각 언어(`--diff-*`, `.digit-diff`, `style.css:50–55, 573–580`)는 데이터 대조 도구라는 성격에 정확히 맞춰진 **의도가 분명한 설계**다. 표 전반에 `tabular-nums`를 적용해 코드·날짜·건수의 세로 정렬을 맞춘 점(`style.css:77–84`), 긴 표를 기본 접힘으로 처리해 페이지 길이를 통제한 점(화성시 29건 collapsed, 스크린샷 03), 스티키 헤더·페이지네이션(`style.css:933–1031`) 등은 "표가 주인공"인 도구의 완성도를 끌어올린다.

다만 **절대 기준**으로 보면 두 축에서 미완이 있다. (1) 브리프가 명시한 모바일(640 이하) 대응이 4~8컬럼 대용량 표에 대해 "가로 스크롤"에만 의존해 핵심 과업(코드 대조)이 소형 화면에서 성립하기 어렵고, 제출된 스크린샷 4장이 모두 데스크톱이라 **모바일 실검증 흔적이 없다.** (2) 조회 결과·오류가 `aria-live`/`role="alert"` 없이 `innerHTML` 교체로만 갱신되고 로딩 상태가 없어, **상태 전이 피드백(특히 스크린리더)이 부재**하다. 이 둘은 배포 전 보완을 권고한다. 그 외 시각적 완성도는 대체로 견고하며, 지적 사항 다수는 폴리시(polish) 수준이다.

**완성도 점수(주관, 절대 기준): 7.5 / 10** — 체계성·시각 언어는 8.5 수준, 접근성·모바일 실사용성이 평균을 끌어내림.

## 2. 잘된 점

1. **디자인 토큰의 일원화** — 색(9단계 gray + 의미색), radius 3종, shadow 3종+focus, transition 2종을 변수화(`style.css:15–59`). 하드코딩 색이 거의 없어 일관성과 유지보수성이 높다.
2. **목적에 종속된 시각 언어** — 앰버를 "바뀐 자릿수 강조" 전용으로 예약하고 파랑(구조)·초록(신규)·빨강(폐지)과 의도적으로 겹치지 않게 격리(`style.css:50–55`). 역방향 안내는 앰버를 피해 파랑 정보색으로 처리(`style.css:638–654`). 색의 의미 규칙이 문서화까지 되어 있다(코드 주석).
3. **데이터 도구다운 타이포 디테일** — 코드/날짜/건수에 `tabular-nums` 적용으로 세로 정렬(`style.css:77–84`), 코드는 박스로 가두지 않고 모노스페이스+자간으로만 구분(`style.css:561–568`, 주석의 판단 근거 명확).
4. **정보 밀도 통제** — 긴 이벤트 표를 헤더 클릭으로 접는 아코디언(`style.css:664–694`), 법정동 표의 스티키 헤더+뷰포트 기준 max-height(`style.css:933–942`)로 검색 폼이 화면에 남게 한 설계. 화성시 29건이 기본 접힘(스크린샷 03).
5. **상태 스타일의 세심함** — 행 상태색(`.row-new/.row-changed/.row-abolished`), 변경 뱃지, 복사 완료 상태(`.copy-btn.copied`, `style.css:811–815`), 페이지네이션 비활성(`:disabled` opacity, `style.css:1021–1024`)까지 상태별 시각이 갖춰졌다.
6. **기본적인 접근성 골격** — 탭에 `role="tablist"/tab/tabpanel"`, `aria-selected`, 로빙 `tabindex`, ←/→ 키 내비게이션(`app.js:16, 27–30`)과 Enter 제출(`app.js:105–113, 238–239, 512–516`)이 구현됨. 폼 `label`–`for` 연결도 전 항목 정상.
7. **입력 검증·빈 상태·오류 상태 존재** — YYYYMM 형식/유효성 검사(`app.js:159–165, 268, 548–557`), "변경 없음" 빈 상태(`app.js:283`, `.no-change`), "검색 결과가 없습니다"(`app.js:608`), 오류 메시지 컴포넌트(`.error-msg`, `app.js:767`)가 모두 마련됨.
8. **반응형 분기의 존재** — 1280/640/400 3단 브레이크포인트로 헤더·탭·폼·타임라인·코드패널을 재배치(`style.css:853–896, 1033–1038`). 넓은 탭은 1280 이하에서 폭 100%로 접음.

## 3. Critical Issues

### C1. 모바일(640 이하) 대용량 표의 실사용성 미완 + 모바일 실검증 흔적 없음
- **무엇**: 지역코드 변환 표(변환전 코드·명칭 / 변환후 코드·명칭 4열, 스크린샷 03)와 법정동 표(8열: 법정동코드·시도명·시군구명·읍면동명·리명·생성일·삭제일·과거법정동코드, 스크린샷 04)는 모바일에서 `.table-wrap { overflow-x:auto }`(`style.css:526–531`)의 가로 스크롤 외에 어떤 적응(열 축약, 카드 뷰, 우선 열 고정)도 없다. 640 미디어쿼리는 셀 패딩만 줄인다(`style.css:894–895`).
- **왜 심각한가**: 이 도구의 **핵심 과업이 "좌(변환 전) ↔ 우(변환 후) 코드 대조"**인데, 360px 화면에서 8열 표는 한 화면에 한두 열만 보이고 좌우를 오가며 스크롤해야 하므로 대조 자체가 성립하지 않는다. 브리프가 "640 이하 모바일 대응 포함"을 매체 요건으로 명시했음에도, 이를 만족한다고 보기 어렵다. 게다가 **제출 스크린샷 4장이 전부 데스크톱(1440 계열)** 이라 모바일이 실제로 검증된 증거가 없다 — 완성도 감사에서 "미검증"은 "미완"으로 간주한다.
- **판단 근거**: `style.css:526–531`(공용 overflow-x만), `style.css:858–896`(640 분기에 표 구조 대응 없음), 스크린샷 03·04(모두 데스크톱).

### C2. 동적 결과·오류의 상태 전이 피드백 부재 (접근성 + 로딩)
- **무엇**: 조회/검색/변환 결과와 오류 메시지는 모두 결과 컨테이너의 `innerHTML` 교체로만 갱신되며(`app.js:283, 608, 767`), 결과 영역에 `aria-live`/`role="status"`/`role="alert"`가 없다(`index.html:78, 103, 170`의 `.result-container`에 라이브 리전 속성 없음). 또한 53,402건 데이터 검색(`index.html:130`)에 로딩·진행 상태 UI가 전혀 없다.
- **왜 심각한가**: (a) **스크린리더 사용자**는 "조회" 버튼을 눌러도 결과가 나타났는지, 오류가 났는지(형식 오류·결과 없음) 알 수 없다 — WCAG 2.1 **4.1.3 Status Messages(AA)** 위반에 해당한다. 공공 행정데이터 도구라는 성격상 접근성 미달은 완성도의 결정적 결함이다. (b) 클릭과 결과 렌더 사이에 로딩 표시가 없어, 대용량 검색이 순간 지연될 때 사용자는 "동작했는지" 확신하지 못한다. 시각 사용자에게도 상태 피드백이 비어 있다.
- **판단 근거**: `index.html:78, 103, 170`(라이브 리전 부재), `app.js:283/608/767`(innerHTML 교체 방식), 로딩 상태 관련 코드 부재(grep에서 spinner/loading UI 미발견).

## 4. Major Issues

### M1. 시도코드 표의 밀도 불균형 — 2열이 660px를 점유하며 우측 대량 공백
- 시도코드 조회는 2열(시도코드·시도명)뿐인데 컨테이너가 660px로 고정(`style.css:220–221`)되어, 스크린샷 02에서 보이듯 시도명("서울특별시" 등) 오른쪽에 **행마다 광대한 빈 공간**이 남는다. 표가 넓게 늘어나 코드와 이름이 오히려 멀어져 대조성이 떨어진다. 표 폭을 콘텐츠에 맞게 좁히거나(예: 420~480px) 유효기간·비고 등 의미 있는 3번째 열을 두어 공백을 해소할 여지.

### M2. 전역 타이틀 < 섹션 타이틀 — 위계 역전
- 페이지 브랜드 `h1`이 1.15rem(`style.css:113–117`)인데 섹션 `h2`는 1.4rem/800(`style.css:236–242`)로 **섹션 제목이 사이트 제목보다 시각적으로 더 크고 무겁다.** "배너 최소화" 의도(`style.css:88`)는 이해되나, 절대 기준에서 최상위 제목이 하위 제목에 눌리는 위계 역전은 완성도 감점 요인. 헤더 브랜드 존재감이 약해 첫인상에서 "무슨 도구인지"의 각인이 약하다.

### M3. 폼 라벨 전역 `text-transform: uppercase` — 한글 라벨에서 무의미·자간만 느슨
- `.form-group label`에 `text-transform:uppercase` + `letter-spacing:.04em`(`style.css:464–470`). 영문 약어(YYYYMM)엔 효과가 있으나 "기준년월/지역 검색/검색 대상" 등 **한글 라벨엔 대문자 변환이 적용되지 않고 자간만 벌어져** 오히려 헐거워 보인다. 한·영 혼합 라벨에서 스타일 규칙이 일관된 결과를 내지 못한다.

### M4. 상시 비어 있는 열이 고정폭을 점유
- 법정동 표에서 "삭제일" 열은 스크린샷 04 전체에서 비어 있고 "리명"도 다수 공백인데, 각 열은 고정폭(`style.css:945–953`)을 상시 점유한다. 데이터 특성상 불가피한 측면은 있으나, 검색 맥락에 따라 열을 조건부 축약/토글하거나 값 없는 셀을 시각적으로 눌러(placeholder dash 등) 밀도를 개선할 여지. 현재는 넓은 표에 빈 열이 겹쳐 시선 낭비가 발생.

### M5. 로딩 상태 부재(시각 관점) — C2와 연계
- C2에서 접근성 관점으로 다뤘으나, 시각 사용자 관점에서도 조회/검색 트리거 후 결과 렌더까지 **어떤 진행 표시도 없다.** 버튼 로딩 스피너나 결과 영역 스켈레톤 같은 최소 피드백이 없어, 대용량 검색의 체감 응답성과 신뢰 피드백이 미완이다.

## 5. Minor Issues

- **N1. 미세 수치 불규칙** — 헤더 `padding:16px 0 15px`(`style.css:93`)의 상/하 비대칭(16 vs 15) 등, 스페이싱이 대체로 체계적이나 일부 값이 임의적. 4/8px 그리드로 정돈 여지.
- **N2. 검색 아이콘 이모지 의존** — 돋보기를 이모지 글리프(`&#128269;`, `index.html:72`)로 렌더. 플랫폼별 색·형태 편차가 있어, 이미 코드 생성/복사 버튼에서 쓰는 인라인 SVG(`index.html:114`)와 톤이 어긋난다. SVG 통일 권장.
- **N3. nav-btn 명시 `:focus-visible` 부재** — 이벤트 헤더엔 `:focus-visible` 아웃라인이 있으나(`style.css:681–684`) 상단 탭 버튼엔 없다. 로빙 탭(활성 탭에 강한 스타일)으로 실질 보완되지만, 명시적 포커스 링을 두는 편이 절대 기준에 부합.
- **N4. 건수 중복 표기** — 법정동 탭에서 상단 "118건 검색됨"과 하단 페이지네이션 "총 118건"이 중복(스크린샷 04). 한쪽으로 정리 가능.
- **N5. 입력 힌트 3중 반복** — YYYYMM 형식이 라벨("기준년월(YYYYMM)")·placeholder("예: 202401")·오류메시지에 모두 반복. 과잉은 아니나 라벨과 placeholder의 역할 분담을 명확히 하면 더 정돈.
- **N6. 코드 생성 패널 다크/라이트 혼재** — 코드 영역만 다크(`style.css:777–789`)인 것은 의도적 대비로 타당하나, 다크 패널 상단 헤더(라이트 gray-50)와 경계에서 톤 점프가 크다. 헤더도 살짝 어둡게 하거나 경계 처리로 매끄럽게 할 여지.

## 6. 수정 권장사항

**C1 (모바일 대용량 표)**
- 640 이하에서 변환/법정동 표를 **카드형 레이아웃**(행→라벨:값 스택)으로 전환하거나, 최소한 **핵심 열(코드·명칭) 우선 고정 + 나머지 접기**를 도입.
- 안 되면 최소 대응으로 `.table-wrap`에 좌우 스크롤 가능 힌트(가장자리 그라데이션/그림자)와 우선순위 열 sticky 좌측 고정.
- **모바일 스크린샷(360/390px) 4탭 실검증**을 감사 산출물에 포함해 "검증됨"을 증거화.

**C2 (상태 피드백·접근성)**
- 각 `.result-container`에 `role="status" aria-live="polite"`를, 오류에는 `role="alert"`를 부여(또는 별도 시각 숨김 라이브 리전 1개를 두고 결과 요약 문장을 주입).
- 조회/검색 버튼에 로딩 상태(disabled + 스피너/문구), 결과 영역 최소 스켈레톤 또는 "조회 중…" 표시 추가.

**M1** 시도 표 폭을 콘텐츠 기준으로 축소하거나 의미 있는 3열 추가. **M2** `h1`을 1.35~1.5rem으로 올려 섹션 h2보다 크게(또는 h2를 낮춰) 위계 정상화. **M3** 한글 라벨엔 uppercase 제거, 영문 약어만 별도 span 처리 또는 라벨 대소문자 규칙 재정의. **M4** 값 없는 셀 대시(–) 표기 + 검색 맥락별 열 토글. **M5** C2의 로딩 처리와 통합.

**Minor** N2·N3·N6부터 저비용 개선(SVG 통일, 포커스 링, 경계 톤). N4·N5는 카피 정리.

## 7. 수정 우선순위

| 순위 | 항목 | 근거 | 예상 비용 |
|---|---|---|---|
| 1 | **C2** 상태·오류 라이브 리전 + 로딩 | 접근성(WCAG 4.1.3) + 전 사용자 피드백. 저비용·고효과 | 낮음~중 |
| 2 | **C1** 모바일 대용량 표 대응 + 모바일 실검증 | 브리프 명시 요건 미충족, 핵심 과업이 소형 화면에서 붕괴 | 중~높음 |
| 3 | **M2** 타이틀 위계 역전 | 첫인상·정보 위계. 1줄 수정 | 매우 낮음 |

## 8. 최종 승인 여부

**조건부 승인 (Conditional Pass)**

완성도는 전반적으로 견고하다 — 디자인 토큰 체계, 목적에 종속된 시각 언어, 상호작용 상태(접힘·복사·페이지네이션·빈/오류 상태)의 성숙도는 이 규모의 정적 도구로서 평균을 상회한다. 다만 **절대적 품질 기준**에서 두 결함은 배포 전 보완을 전제로 한다:

1. **C2 — 상태·오류의 접근성/로딩 피드백 부재** (우선 처리, 저비용)
2. **C1 — 모바일 대용량 표 실사용성 및 실검증 부재** (브리프 명시 요건)

위 2건 해소 시 무조건 승인 가능 수준이며, Major·Minor는 후속 폴리시로 순차 반영 권장. 시각적 완성도 자체는 승인 기준을 충분히 통과한다.
